# Agent 子任务重试与任务级累计 Diff

## 分类与状态

- 分类：功能优化 / 用户体验优化。
- 状态：代码已实现，自动化与本地 Web Browser 回归通过，待真实 Provider、Electron、懒猫及故障注入实机回归。
- 对应台账：`REQ-20260809-001`。
- 技术方案：`docs/Agent子任务重试与任务级累计Diff技术实现方案.md`。

## 背景与目标

当前主 LLM 的自动重试函数在每次 `callLLMWithRetry()` 调用时重新计数，但系统没有可持久化、可恢复的 sub task 实体。运行事件和界面主要依赖 `loop_index` 关联重试记录，无法稳定表达“同一个 sub task 内累计重试，进入下一个 sub task 后重新计数”。

文件写入方面，自动确认模式已经允许多个预览工具在不同 Loop 轮次依次应用；手动确认模式在首个未应用预览生成后结束 session。现有 operation set 已按 session 保存多条记录，但最终消息和 Diff 卡仍以单个 `operation_set_id` 为主要关联方式，通常只展示最近一批。任务在失败、中断或取消时，也没有独立于最终助手消息的任务级累计 Diff 入口。

本次优化计划建立两个稳定边界：

1. 用服务端生成的“执行段”承载 sub task 重试范围。一个执行段对应一次“读取已有工具结果后，请求主 LLM 决定下一步”的过程；同一执行段内自动重试最多额外 5 次，进入下一个执行段后重新计数。
2. 用“任务变更集”聚合同一 Agent session 的全部文件和目录操作。底层继续保留不可变的分批 operation set，界面只显示一个累计 Diff 入口。

这里不引入由模型自由声明的高层任务清单。模型请求在失败前可能还没有产出工具名称，依赖模型生成 sub task ID 会让恢复和去重失去确定性。界面可在工具返回后把执行段标题补充为“读取文件”“修改笔记”等真实动作。

## 范围与非目标

### 范围

- 主 LLM 自动重试的执行段归属、计数、持久化事件和历史恢复。
- 每个执行段一条模型重试记录；同一执行段内更新次数，不覆盖其他执行段。
- 同一 session 内创建、修改、重命名、移动文件，以及新建、重命名、移动目录的分批执行与累计展示。
- 自动模式逐批安全应用，手动模式逐批确认并从原 checkpoint 继续。
- 完成、可恢复失败、不可恢复失败、中断和取消后的累计 Diff 可见性。
- 继续任务时复用已完成工具结果、已应用批次和未完成执行段，避免重复写入。

### 非目标

- 不开放删除文件或目录。
- 不把多个用户消息或多个 Agent session 合并成一个 Diff。
- 不改变知识库 `/api/chat`、画布非 Agent 对话或对外 MCP 变更审核流程。
- 不引入 Git worktree、容器或完整工作区副本。
- 不把任务级累计 Diff 设计成数据库事务式的“一次性全量提交”；自动模式和手动模式仍按批次完成真实写入。
- 不恢复当前关闭的“已使用资料 / 文件变更”回执卡开关。

## 方案比较

### 方案一：复用 Loop 轮次和现有 operation set 做前端聚合

- 做法：把 `loop_index` 直接当作 sub task ID，前端按 session 汇总现有 operation set。
- 工作量：中。
- 风险：中高。刷新与继续后 Loop 轮次不能完整表达未完成执行段；手动模式仍会在首个预览后结束；工具已写入但 checkpoint 尚未提交时仍可能重放。
- 复用内容：现有 `agent_run_events`、`listOperationSetsBySession()` 和 DiffDialog。
- 结论：可快速改善显示，无法可靠处理手动续跑和中断幂等，不建议作为最终方案。

### 方案二：持久化执行段 + 任务变更集，分批 operation set 保持不变

- 做法：为 session 增加持久化执行段和唯一任务变更集；每次主 LLM 决策请求归入一个执行段，每个预览工具产生一个带顺序号的批次 operation set。服务端按任务变更集输出累计视图，前端只渲染一张 Diff 卡。
- 工作量：大。
- 风险：中。需要同时调整状态机、checkpoint、应用接口、SSE 和历史恢复，但可以沿用现有安全写入与 Diff 组件。
- 复用内容：现有 session、run lease、checkpoint、operation set、文件修订、应用/回滚和 DiffDialog。
- 结论：推荐。它能满足分段重试、分批写入、手动续跑、失败可审查和单卡累计展示，数据迁移也可以保持增量兼容。

### 方案三：为每个 Agent 任务创建隔离的临时工作区

- 做法：所有批次先写入 session 专属副本，任务结束后再合并到正式工作区。
- 工作量：很大。
- 风险：高。`read_file`、`analyze_folder`、搜索、索引、图片存储、文件监听和跨平台路径都需要支持覆盖层，目录移动和外部编辑冲突也会显著复杂化。
- 复用内容：只能复用部分 Diff 与应用逻辑。
- 结论：当前需求不要求隔离式原子提交，这个方案会扩大改造范围，不采用。

## 推荐方案的状态模型

```text
Agent session
├─ execution segment #1
│  ├─ LLM request window #1：自动重试 0…5 次
│  └─ tool result：读取或检索
├─ execution segment #2
│  ├─ LLM request window #1：自动重试 0…5 次
│  └─ operation batch #1：文件修改
├─ execution segment #3
│  ├─ LLM request window #1：自动重试 0…5 次
│  └─ operation batch #2：目录移动
└─ task change set：累计展示 batch #1 + batch #2
```

### 执行段

- 服务端在主 LLM 请求前创建或恢复执行段，分配稳定 ID 和顺序号。
- 同一次 LLM 调用的自动重试共用执行段 ID；请求成功并形成工具调用或最终回复后，该执行段结束。
- 工具结果写回上下文后，下一次主 LLM 请求创建新执行段，自动重试从 0 开始。
- 自动重试耗尽后点击“继续任务”，仍恢复未完成的执行段，但创建新的请求窗口。新窗口重新获得 5 次自动重试额度；界面仍保持该执行段一条重试记录，并在展开详情中保留前一窗口的失败次数。
- 执行段标题先显示“规划下一步”；收到真实工具调用后按工具名称补充标题。失败前没有工具结果时不推测动作名称。

### 任务变更集与批次

- 每个 Agent session 最多一个任务变更集，作为累计 Diff 的稳定 ID。
- 每次 `create_note`、`preview_file_revision`、`preview_patch_files` 或 `preview_file_operations` 仍创建独立 operation set，并写入任务变更集 ID、批次顺序号和触发它的执行段 ID。
- 第一次触及文件或路径时保存任务开始前快照；每个批次完成后更新该资源的最新快照。累计 Diff 以“任务首次触及前 → 当前已应用或待确认结果”生成，避免同一文件被多次修改时展示多张重复卡。
- 创建后重命名只显示最终路径的新建结果；连续移动只显示初始路径到最终路径；移动后修改同时显示路径变化和正文净变化。
- 已废弃批次不进入累计净 Diff，但保留在任务审计记录中。应用失败或冲突批次在同一 Diff 中标记状态，不伪装成已经写入。

### 自动模式

- 每个批次通过现有 Hash、路径和图片存储检查后立即应用。
- 应用结果与任务变更集必须先持久化，再允许 Loop 进入下一执行段。
- 任务失败、中断或取消时，累计 Diff 显示所有已应用批次；没有待处理操作时只提供查看和安全回滚能力。

### 手动模式

- 新批次生成后，session 进入新的 `waiting_operation_confirmation` 状态，不再写成 `completed`。
- 同一张累计 Diff 卡显示历史已应用批次与当前待确认批次。用户“应用并继续”后，服务端应用当前批次、写入工具结果、提交 checkpoint 并唤醒原队列任务；Agent 从原 session 继续。`agent_resume_jobs` 仍只处理 interaction。
- 用户“废弃并继续”后，服务端把废弃结果写回原工具调用，Agent 可调整方案或结束任务。用户显式停止后不自动续跑。
- 任务因模型或其他问题暂停时，累计 Diff 仍可打开。已经存在的待确认批次可以手动应用或废弃；应用操作本身不绕过文件 Hash、路径和图片安全检查。

## 实施顺序

1. 增加增量数据库迁移，建立执行段、任务变更集、批次关联和写入幂等约束；旧 operation set 保持可读。
2. 调整 Agent Loop 与 checkpoint，在主 LLM 请求前创建/恢复执行段，在每个工具结果和批次状态落库后提交可恢复进度。
3. 调整手动确认状态机和任务队列唤醒，使“应用并继续 / 废弃并继续”恢复原 session；`agent_resume_jobs` 继续只用于 interaction；自动模式继续逐批应用。
4. 增加任务变更集聚合服务，维护首次快照、最新快照、路径演变、批次状态和逆序回滚顺序。
5. 扩展 session 详情与 SSE 白名单，只传执行段标识、重试摘要、变更集摘要和按需详情入口。
6. 前端工具链按执行段渲染模型重试；消息和错误状态按 session 关联同一张累计 Diff 卡，去除“只取最近 operation set”的主路径。
7. 增加旧数据兼容：没有执行段或任务变更集的历史 session 继续使用现有 Loop 和单 operation set 展示。
8. 完成自动化、故障注入和 Web/Electron/懒猫实机回归后，再更新状态为已完成。

## 风险检查与回退

- Provider 或网络故障：执行段、checkpoint 和批次结果先落库，错误发生后仍可恢复和查看 Diff。
- 数据量增长：累计 Diff 只保存每个资源的首次与最新快照，列表和 SSE 只返回摘要，正文按文件加载。
- 回退成本：迁移只新增表、字段和索引；旧 operation set 与单卡展示保持兼容。若新聚合路径需要停用，前端可回退到最近 operation set，历史批次数据无需删除。
- 最脆弱的前提：用户所说的 sub task 可能指高层语义任务清单，而本方案把它定义为确定性的主 LLM 执行段。若产品需要用户可见、可编辑的高层计划，需要另行设计 planner、任务依赖和完成条件，不能仅靠本次重试模型补足。
