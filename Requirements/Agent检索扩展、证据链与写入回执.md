# Agent检索扩展、证据链与写入回执

## 分类与状态

- 分类：功能优化 / 用户体验优化
- 状态：已完成

## 背景

用户自然语言中的项目名、功能名和笔记标题往往不一致。当前 Agent 可能把用户原话或仓库名作为单一关键词检索，未命中就直接要求用户补充资料。用户提供 GitHub 仓库 URL 后，Agent 也可能先依赖关键词搜索；网页抓取、知识库读取和系统导入的结果没有统一的可追溯记录。成功获取的外链材料还可能被后续一次空搜索覆盖，最终误报“没找到”。

写作任务若已存在候选文章，但用户没有说明要新建还是修改旧稿，Agent 也需要先确认目标，不能在未确认时自行新建或改写。

现有 Agent 已在执行期发送 `tool_start`、`tool_done` 事件，也已通过操作集和 DiffDialog 承载文件预览、应用与回滚。本需求补齐从工具调用到最终回答、历史追问和写入结果的证据链。

## 目标

1. 检索前保留用户原始表述，并生成 3 个互不重复的查询变体；初轮证据不足时再补 2 个，单次任务最多 5 个查询。
2. 让用户提供的精确 GitHub 仓库 URL 优先走直连读取，不把搜索引擎是否收录当作仓库信息可得性的前提。
3. 为知识库检索、文件读取、联网搜索、显式 URL 读取和文件写入保存可查询的脱敏回执。
4. 让 Agent 只能依据成功回执表述“已读取、已找到、已创建、已修改”；失败、空结果、待确认预览和已应用写入使用不同文案。一次成功的目标读取不能被后续空搜索降级为“未找到”。
5. 让最终消息明确列出实际来源与文件变更，用户追问工具历史时返回真实调用记录。
6. 发现已有候选文章且新建/改写目标不明确时，使用提问卡片确认用户意图。

## 方案范围

1. 新增检索查询规划器。首轮产生 3 个查询：原始词、功能/意图改写词、中文或同义表述词；去重后批量检索。结果无直接命中、最高证据不足或候选冲突时，再产生最多 2 个补充查询。每个查询记录改写来源、结果数和停止原因。
2. 新增统一证据回执，至少包含调用 ID、工具名、请求摘要、来源类型、规范化 URL 或路径、Provider、状态、耗时、正文长度、内容哈希、截断摘要和脱敏错误码。
3. 显式 GitHub 仓库 URL 采用仓库信息与 README 的直连链路；直连成功即建立目标材料状态。API 限流、README 缺失、页面抓取失败和搜索无结果分别记录，后续空结果不得覆盖已成功读取的目标材料。
4. 将同一会话的回执写入可查询日志。Agent 被问及历史调用时，先读取回执，再回答实际 query、命中结果、来源和失败原因。
5. 最终回复旁展示紧凑的“已使用来源”和“文件变更”摘要。执行中保留简短进度，完成后不暴露原始 Prompt、密钥或大段工具输入输出。
6. 发现最近会话存在候选文章、但用户没有明确“新建”或“修改哪篇”时，先读取候选的元数据并调用 `ask_question_card`。用户明确指定路径、明确说继续修改且只有一个承接目标时，直接进入读取与预览修订。
7. 文件操作文案严格区分“已生成待确认预览”“已应用修改”“写入失败”“已回滚”，成功写入必须附带文件路径和 operation set / Diff 入口。

## 非目标

- 不改变删除禁用、预览确认、会话授权和 MCP 授权边界。
- 不把完整网页正文、密钥、Cookie、认证头或原始模型 Prompt 写入可见日志。
- 不承诺第三方搜索引擎的收录、排名或可用性。

## 实现结果

- `search_knowledge` 与 `web_search` 保持单个 `query` 入参，由服务端在每个 Agent task、每个来源内固定执行原词在首位的 3 个查询；初轮没有足够证据时才补 2 个。相同任务的重复调用和换词调用只返回已缓存的合并结果，不能绕过来源级 5 词上限。
- 规划器优先使用当前任务选中的 LLM 生成 `initial_queries` 与 `fallback_queries`；配置或请求失败时回退为规则查询，不中断任务。每条查询保存阶段、状态、耗时、结果数、规范化路径或 URL、内容哈希和脱敏错误码。
- 用户显式输入 URL 时，直连解析完成后立即写入 `explicit_url` 成功或失败回执。GitHub 根仓库链接先确认仓库，再直连读取 README，并区分仓库不存在、README 缺失、限流和抓取失败。成功回执会进入 Agent 上下文；最终文本若与之冲突，服务端替换为“已读取链接材料，联网搜索没有补充结果”的确定性结论并记录修正回执。
- `get_task_activity` 只读当前 session 的回执与工具日志，返回实际查询顺序、执行状态和未执行工具；会话查询接口只返回脱敏回执。
- 最终助手消息的 `meta.research_summary` 与 `meta.write_summary` 由服务端生成。界面在消息下方展示“已使用资料 / 文件变更”卡片，不展示正文、Cookie、密钥或原始 Prompt。
- 同一对话出现最近创建文章、但本轮未指明新建或改写目标时，服务端直接调用既有提问卡片；回答会写入 task 状态，选择现有文件后强制先读该文件并使用完整修订预览。唯一候选且明确“继续修改”不再额外打断。

## 验收

1. 用户输入的自然语言项目描述与知识库标题不一致时，日志显示首轮 3 个改写查询；低置信或零命中才扩展到第 4、5 个查询，永不超过 5 个。
2. 输入公开 GitHub 仓库 URL 时，即使关键词搜索为空，也能显示直连读取的仓库/README 回执或明确的直连失败原因；直连成功后最终回复不得出现“没有找到该仓库”。
3. 用户问“第一轮搜索关键词是什么”时，答案与日志中的真实 query、改写来源和调用顺序一致；没有调用时明确说明未调用。
4. `web_search` 返回空、Provider 限流、URL 抓取失败、README 缺失四种状态均有不同错误码和用户文案。
5. 未成功读取的材料、未执行的工具调用和待确认的文件预览都不会被最终回复表述为已完成。
6. 存在多个候选文章或新建/改写意图不明确时，Agent 必须展示提问卡片；用户的选择决定后续目标，不能自行新建或改写。
7. 新建、修改、应用、回滚和失败的文件操作均能从消息摘要定位到文件路径和操作状态。
8. 为本次对话中的“GitHub URL → 3+2 查询规划 → README → 文章目标确认 → 写作文件修改”路径建立自动化回归测试。
