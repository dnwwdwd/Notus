# 需求文档规范

本目录用于记录仓库中的非 bug 需求，不记录 bug。

## 目录用途

- `需求总台账.md`：需求总台账，记录每次收到的需求、分类、状态和归档位置。
- 业务名称文档：单条需求的详细记录，适用于需要保留背景、目标、范围、决策和验收标准的需求。

## 分类规则

- 功能需求：
  - 新增能力、接口、页面、流程、配置或规则。
  - 进入 `需求总台账.md`，必要时新增业务名称需求文档。
- 功能优化：
  - 对已有能力做增强、补强、限制收紧、流程调整或策略升级。
  - 进入 `需求总台账.md`，必要时新增业务名称需求文档。
- 用户体验优化：
  - 对交互、视觉、提示、默认值、操作路径和理解成本的优化。
  - 进入 `需求总台账.md`，必要时新增业务名称需求文档。

## 记录规则

1. 每次收到需求，先写入 `需求总台账.md`。
2. 需求复杂、持续时间长、涉及范围广时，再新增独立的业务名称需求文档。
3. 如果一个请求同时包含 bug 和优化项，必须拆分为多条记录。
4. bug 不写入 `Requirements/`，统一记录在 `docs/Bug台账.md`。
5. 需求完成后，要回填状态、落地文档和验证结果。

## 记录格式

### 简版需求

单文件、无持久化状态、无跨端差异的需求可以只在 `需求总台账.md` 记录分类、范围、状态、落地文件和验证结果。交付说明仍需列出检查过的文档与实际执行的验证。

### 跨模块需求

命中任一情况时必须创建或补全业务名称需求文档：同一资源有多个写入入口或读取方；状态跨 API、SSE、确认卡、缓存或后台任务传播；涉及 Agent、检索、索引、图片、文件、Skill、MCP；涉及 Web、Electron、懒猫、权限、密钥或运行时能力差异。

跨模块记录使用下面的结构。字段只填写实际受影响的内容，空泛地罗列所有模块不构成影响分析。

```md
# 业务名称标题

## 分类与状态

- 分类：功能需求 / 功能优化 / 用户体验优化。
- 状态：进行中 / 已完成 / 已搁置 / 已取消。

## 背景与目标

## 范围与非目标

## 影响分析

| 维度 | 已确认内容 |
|---|---|
| 写入入口 | API、设置页、Agent Tool、确认卡或后台任务。 |
| 读取方与状态传播 | 页面、输入控件、Prompt、缓存、重启恢复与刷新方式。 |
| 边界 | 权限、密钥、失败、取消、回滚与平台差异。 |
| 已检查但不受影响 | 模块及不需要修改的原因。 |

## 行为验收矩阵

| 场景 | 前置条件 | 操作 | 预期结果 | 验证状态 |
|---|---|---|---|---|

## 文档同步

- 已更新：列出实际变更的 PDD、PRD、UI Guide、流程文档、进度或台账。
- 未更新：列出已检查但不受影响的相关文档和原因。

## 实现与验证

- 代码与配置：
- 已执行命令及结果：
- 待实机回归：
```

跨模块 bug 仍只写入 `docs/Bug台账.md`。条目需在“根因 / 发现”或“验证”中覆盖影响范围、相关流程检查和行为验证，不创建需求文档。

## 状态建议

- `待评估`
- `进行中`
- `已完成`
- `已搁置`
- `已取消`

`已完成` 表示影响分析、相关文档和可执行验证均已完成。存在真实环境、凭据或平台限制的用户路径时，状态应使用“已完成，待实机回归”或在记录中明确待回归项，不能用 lint、构建或静态断言替代行为验证。
