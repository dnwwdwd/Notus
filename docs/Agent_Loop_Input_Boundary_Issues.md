# Agent Loop 输入边界问题整理

日期：2026-06-30

## 背景

当前创作页 Agent Loop 已经把用户任务、当前打开文档、当前文章路径、当前块快照、附件和历史会话上下文合并到同一轮执行链路中。这样有利于 Agent 理解工作区状态，但也暴露出一个边界问题：部分本应只针对“用户本轮显式输入”的预处理逻辑，实际扫到了 Agent 执行上下文和历史任务上下文。

这会让 Agent 在用户没有明确要求时触发副作用，例如自动解析当前文档里的网页链接，或把新上传的无关 PDF 过早关联到上一轮写作任务。

## 问题一：当前文档中的链接被自动解析

### 用户现象

用户在创作页发送：

```text
根据我的笔记生成一个文档介绍我自己
```

用户本轮 prompt 没有携带网页链接，但当前打开文档中包含网页链接。Agent Loop 启动后仍自动触发“解析网页链接”。

### 已确认根因

前端构造给 Agent Loop 的 `goal` 时，会把用户任务和当前文档上下文拼在一起：

```text
用户任务：...

当前打开文档：...
当前文章路径：...

当前创作页文本块快照：
@b1 ...
<当前文档内容>
```

后端 `/api/agent/loop/start` 在创建 session 前调用 `parseAgentInputSources()`，但传入的是完整 `goal`：

```js
parseAgentInputSources({
  conversationId,
  attachments: body.attachments || [],
  text: goal,
})
```

`parseAgentInputSources()` 会无条件从 `text` 中提取 URL 并解析网页正文。因此当前文档块快照里的 URL 被误认为是“用户本轮输入中的 URL”。

### 为什么需求口径没生效

需求和 PRD 口径已经写明应解析“用户输入中的网页链接正文”或“用户显式提供 URL 的正文”。但实现只在前端展示消息时保留了 `display_query`，后端解析入口仍使用完整 `goal`。

也就是说，当前只做了“展示层拆分”，没有把拆分贯穿到“附件/网页链接解析”这个副作用流程。

## 问题二：上传无关 PDF 后过早关联上一轮写作任务

### 用户现象

同一对话中，第一轮用户要求 Agent 根据现有笔记写一个自我介绍文档。第二轮用户只上传了一个和自我介绍无关的 PDF，没有明确说明要把 PDF 加入自我介绍。

Agent 使用提问卡片询问：

- 是否需要将上传文档加入自我介绍文档，还是只解析文档内容。
- 如果要加入自我介绍文档，需要加到哪里。

### 判断

这个行为不算完全错误，因为同一 conversation 的历史目标确实提供了“自我介绍文档”上下文。但产品体验上不够合理，属于过度承接上一轮写作目标、过早使用提问卡片。

用户本轮只有附件，没有明确写入指令时，更合理的默认行为应该是解析并总结附件，或用普通澄清询问用户希望如何处理附件，而不是直接假设它要进入上一轮文档。

### 可能根因

当前 Agent Loop 把以下内容放在同一执行上下文里：

- 上一轮用户目标和对话历史。
- 当前会话已解析附件。
- 当前文档信息和授权写入范围。
- 本轮上传附件。
- 本轮用户文字。

系统 prompt 又鼓励 Agent 在信息不足时使用 `ask_question_card`。当本轮只有附件或意图很弱时，Agent 容易把历史任务当成仍在延续的主任务，然后把“是否写入上一轮文档、写到哪里”当成缺失槽位。

这里的问题不是上下文本身不可用，而是缺少“本轮显式意图优先”的路由规则。

## 问题本质

当前 `goal` 同时承担了三种职责：

1. Agent 执行目标。
2. 当前文档、块快照和工作区上下文容器。
3. 用户本轮输入源解析对象。

第 3 项是错误边界。附件和网页链接解析是有副作用的预处理，只应基于用户本轮显式输入和用户上传/粘贴的附件，不应扫描 Agent 执行上下文、当前文档快照或历史任务。

同时，提问卡片是结构化澄清工具，应服务于已经明确的任务，而不应在本轮意图未定时直接把历史写作任务当成主线。

## 已实施方案

### 1. 拆分请求字段

前端进入 Agent Loop 时同时传：

- `goal`：Agent 执行目标，仍可包含当前文档名称、路径、块快照等上下文。
- `user_query` 或 `input_text`：用户本轮原始输入，只包含用户实际在输入框提交的文字。
- `attachments`：用户本轮上传、粘贴或长文本转出的附件。

当前实现中，创作页和知识库页都会在启动 Agent Loop 时传入 `user_query` 与 `display_query`。`useAgentLoopController()` 会继续兼容 `user_query/userQuery/input_text/inputText/display_query/displayQuery` 这些字段，保证旧调用不会把完整 `goal` 当成解析输入。

### 2. 限定解析来源

`/api/agent/loop/start` 调用 `parseAgentInputSources()` 时，不再传 `goal`，只传用户本轮原始输入：

```js
userInputText: body.user_query || body.input_text || body.display_query || ''
```

附件解析继续使用 `body.attachments`。

这样当前文档块快照中的 URL 不会被自动解析；用户本轮明确输入 URL 时仍会解析。

兼容旧客户端时，后端只按 `user_query -> input_text -> display_query -> ''` 取值，不再 fallback 到 `goal`。因此如果旧调用只传完整 `goal`，URL 解析会跳过，避免再次扫描当前文档、块快照或历史上下文。

### 3. 附件无指令时调整默认意图

当本轮有附件但用户没有明确写入、合并、参考、改文档等指令时，默认按“读取/总结附件”处理，不自动关联上一轮写作任务。

只有用户显式表达以下语义时，才把附件和当前文档写入任务关联：

- “把这份 PDF 加进文档”
- “参考这个附件改写”
- “根据附件补充自我介绍”
- “用这份资料更新当前文章”

当前实现采用两层约束：Prompt 明确“用户本轮输入优先于历史任务”，工具层在 `ask_question_card` 执行前检查本轮是否有附件/解析来源、用户任务是否缺少明确写入意图、卡片内容是否在追问写入当前文档/自我介绍的位置。如果命中，则返回 `QUESTION_CARD_REQUIRES_EXPLICIT_WRITE_INTENT`，要求模型先总结/说明附件，或用普通文本询问用途。

### 4. 收紧提问卡片触发边界

提问卡片适合：

- 任务已明确，但缺少必要结构化槽位。
- 用户明确要求“先问我几个问题”。
- 多步骤写入任务必须获得用户选择后才能继续。

提问卡片不适合：

- 用户只上传附件、没有说明用途。
- 本轮意图还没有确定。
- Agent 仅凭历史任务猜测用户要继续写入。

这类场景应先普通澄清，或默认给出附件摘要并等待下一步指令。

如果用户明确说“把这个 PDF 加入当前文档”“根据附件补充自我介绍”等，工具层会放行写入位置类提问卡片，保留必要的结构化确认能力。

## 当前状态

- 当前打开文档或块快照里的 URL 不再作为网页解析输入。
- 用户本轮输入中显式提供 URL 时，仍会进入网页正文解析。
- 附件上传本身仍会解析；限制的是“没有写入指令时自动绑定到上一轮写作任务”。
- `ask_question_card` 不被禁用，只收紧到任务明确且缺少结构化槽位，或用户主动要求先提问的场景。
- `goal` 仍作为 Agent 推理和执行上下文保留，用于当前文档、路径、块快照和授权范围；但它不再承担输入源解析职责。

## 验收标准

1. 当前打开文档包含 URL，但用户 prompt 不包含 URL 时，Agent Loop 不触发网页链接解析。
2. 用户 prompt 明确包含 URL 时，Agent Loop 仍能解析网页正文。
3. 用户只上传 PDF 且没有文字指令时，Agent 默认总结或说明附件内容，不直接询问写入上一轮文档的位置。
4. 用户明确说“把这个 PDF 加入当前文档/自我介绍”时，Agent 可以使用提问卡片确认写入位置。
5. 历史对话上下文仍可用于理解用户意图，但不得覆盖本轮显式输入优先级。
6. 知识库页不启用解析附件模式的现有边界保持不变。

## 需要覆盖的回归测试

- `goal` 包含 URL、`user_query` 不包含 URL：不调用 URL 解析。
- `user_query` 包含 URL：调用 URL 解析。
- `goal` 的块快照包含多个 URL：不自动解析。
- 本轮仅上传附件且无文字：不默认生成写入当前文档的位置提问卡片。
- 本轮上传附件并明确“加入当前文档”：允许结构化提问写入位置。
