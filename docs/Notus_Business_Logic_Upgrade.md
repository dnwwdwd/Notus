# Notus 业务逻辑升级说明

> 更新时间：2026-06-14
> 适用范围：本轮知识库、创作工作台与桌面工作区的业务逻辑升级

---

## 1. 背景

本轮调整不再按“零散页面改动”记录，而是按业务功能重新归类。目标不是单纯修某个控件，而是把知识库、创作和文件工作区之间的核心协作链路补完整，让用户在同一份文档上下文里连续完成“查看、提问、创作、定位原文”。

---

## 2. 全局工作区状态

### 2.1 统一状态项

当前桌面工作区统一维护以下状态，并持久化到本地：

- 当前文档 `activeFileId`
- 当前业务页 `activePage`
- 文件树展开目录 `openFolders`
- 侧边栏折叠状态 `sidebarCollapsed`
- 侧边栏文件树 / 大纲 tab `sidebarActiveTab`
- 侧边栏文件树 / 大纲滚动位置 `sidebarScrollByTab`
- 待消费的来源定位目标 `pendingCitation`
- 文件页、知识库页和创作页的浏览位置锚点

### 2.2 当前行为

- 无论用户在文件页、知识库页还是创作页打开文档，系统都会记住“当前文档”。
- 用户切换到其他业务页后，不需要再次二次打开同一篇文档。
- 顶部搜索、侧边文件树、新建文件等入口，都会优先延续当前业务页逻辑，而不是强制跳回文件页。
- 侧边栏折叠状态、文件树展开状态、文件树 / 大纲 tab 和各 tab 滚动位置会在桌面工作区内保持一致。
- 文件页、知识库页和创作页共享同一文档的最近阅读位置：编辑器按文本锚点恢复，创作页按 block id 或正文文本恢复，并保留锚点在视口中的相对位置。
- 普通滚动停止后才保存位置，切页开始时同步写入；新页面完成恢复前不会用初始化顶部覆盖已有记录。
- 来源卡片定位、URL 行号定位和待消费引用定位优先于历史浏览位置。

## 3. 知识库问答升级

### 3.1 检索与回答链路

知识库问答从“给出来源列表”升级为“基于证据自然回答”，核心规则如下：

- 在正式检索前先做一次轻量查询规划，输出意图、独立问题、扩写问题、关键词和标题线索。
- 检索不再只跑单条 query，而是并行组合原始问题、改写问题、扩写问题和标题线索做多路召回。
- 文档标题、文件路径和标题层级会一起进入检索链路，标题命中的文件会再做二次 chunk 召回。
- 优先提升当前已打开文档的召回权重。
- 在混合检索结果之上按章节聚合，生成 `sections` 级证据，而不是只返回离散片段。
- 命中 seed chunk 后，会补齐同 heading 下的邻近上下文，形成可直接回答的证据包。
- 在回答前判断证据是否充分；证据不足时返回保守结论，不放任模型自由发挥。
- 回答保持自然、直接、克制，不固定套用“结论 / 整理 / 证据”模板。
- 流式事件中继续返回来源片段，同时附带章节聚合结果与检索统计。
- 如果只命中文档标题但正文证据偏弱，回答会明确说明“已定位到相关文档，但正文证据有限”。
- 命中 `clarify_needed` 时，不再返回单条文字追问，而是创建知识库专用 `conversation_interactions` 抽屉，优先补齐对象、对比对象、时间范围和检索范围；答完后先回顾，再点击“开始检索”续跑。

### 3.2 历史与追问口径

- 知识库页历史仍然保留在全局空间，但页面默认进入新对话，不再自动恢复最近一条旧会话。
- 只有用户主动从历史抽屉里选择某条旧会话，后续消息才会继续挂到对应 `conversation_id`。
- 历史抽屉支持删除整条会话；删除前二次确认，删除当前会话后回到新对话空态。
- 追问改写会同时参考最近若干轮 `user + assistant`，不再只依赖用户问题本身。

### 3.3 来源点击行为

- 来源卡片点击后不再跳到文件页。
- 如果当前处于知识库页，系统会直接展开左侧编辑区并定位到对应原文区域。
- 定位后会自动滚动并保持高亮，直到用户手动关闭。
- 同一套来源定位逻辑已抽成共享工具，文件页也能消费同样的定位目标。

### 3.4 业务价值

- 用户不需要再“一个一个点来源自己拼答案”。
- 知识库页本身即可完成“提问 -> 回答 -> 看证据 -> 回到原文”的闭环。

## 4. AI 创作工作台升级

### 4.1 后台事实补充与前台风格来源

创作页当前采用一条后台事实通道和一条前台风格通道：

- 事实参考：由系统后台自动补充，不再在前台单独展示配置。
- 风格来源：继续由用户控制，决定语言表达、节奏和措辞参考哪些历史文章。

### 4.2 当前文档参与创作

- 如果用户是从现有文档进入创作，当前文档会作为优先上下文参与大纲生成与 AI 改写。
- 大纲生成接口会同时读取当前文档、后台事实补充结果和风格样本。
- Agent 运行时默认也会优先围绕当前文档与相关知识上下文工作，避免无边界乱搜。

### 4.3 块级定向改写

- 输入框中的 `@` 会匹配当前文档块，插入 `@bN` 形式的块引用。
- 当用户明确指定块后，AI 只能修改被引用的块，不能越权改动其他块。
- 该限制在 Agent 的块白名单校验中生效，不只是前端提示。

## 5. 文档语义分块系统

### 5.1 分块原则

旧分块方式更偏向字符串拆段，容易把结构相关的内容切碎。本轮调整后，分块遵循：

1. 优先按标题层级划分。
2. 如果文档标题层级不足以支撑稳定分段，则回退到 AST 语义分块。
3. 如果解析失败，再回退到基础文本分段。

### 5.2 分块特征

每个块除了正文内容，还会携带：

- `headingLevel`
- `headingPath`
- `lineStart`
- `lineEnd`
- `semanticGroup`

### 5.3 业务价值

- 创作页块粒度更接近真实章节语义。
- 知识库来源定位与章节聚合可复用同一套结构信息。
- 服务端解析文章时不再把 AST 解析依赖打进客户端包。

## 6. 侧边栏与桌面布局

### 6.1 当前口径

- 侧边文件树支持全局折叠/展开状态持久化。
- 侧边目录展开状态全局保留。
- 侧边文件树 / 大纲 tab 与两个 tab 各自滚动位置全局保留。
- 文件页、知识库页和创作页保留页面级浏览位置，并通过文档级记录共享最近阅读位置。
- 文件页和知识库页共用真实 H1-H6 大纲状态；知识库 AI 未就绪时，大纲和左侧文章仍可查看。
- 顶部、侧边栏、知识库、创作页围绕同一份当前文档状态协同。

### 6.2 版本边界

- 本版本按桌面工作区设计，Web 与 Electron 都设置 1360 × 800 的最小宽高。
- 本轮不做移动端适配，也不提供平板/手机降级布局方案。
- 知识库页和创作页分栏需要保留编辑区与聊天区的最小可用宽度，避免右侧 AI 输入框在窄宽度下散开；本轮不单独改动全局 `1360px` 最小宽度和侧边栏壳层行为。

## 8. Workspace Agent 第一阶段

### 8.1 文件系统与数据库关系

当前业务口径已调整为：Markdown 文件系统是真实来源，SQLite 数据库只保存索引、元数据、会话、预览和运行状态。

- `files` 表不保存 Markdown 正文，只保存路径、稳定身份、hash、mtime、frontmatter、tags、heading outline 等元数据。
- `chunks.content` 是检索副本，用于 FTS5、向量化和来源定位，不作为文档正文来源。
- 知识库回答在 chunk 命中后会反查 `file_id`，再从文件系统读取真实 Markdown 正文。
- 如果读取到的文件 hash 与数据库中的 `files.hash` 不一致，本次仍使用最新文件内容，并把结果标记为 `stale_index`。

### 8.2 向量完成状态

文本索引的完成状态以文件为单位记录：

- `files.indexed = 1`：该文件本轮文本 chunks 和文本向量都已成功写入。
- `files.indexed = 0` 且 `index_error` 为空：文件待索引或待重试。
- `files.indexed = 0` 且 `index_error` 非空：该文件索引失败，通常是 Embedding API、网络、余额或维度问题。
- `files.retry_count` 记录失败重试次数。
- `chunks.source_hash` 记录 chunk 生成时对应的文件 hash，用于判断 chunk 是否来自当前文件版本。

如果 Embedding 在某个文件上失败，系统仍会保留该文件的 chunks 和 FTS5 全文索引；该文件可以通过全文检索被找回，但不能参与语义向量召回，直到后续重试成功。

图片索引有独立状态：`images.embedding_status` 会记录图片向量的 `pending/done/skipped/failed`。

### 8.3 重建索引与失败降级

重建索引接口通过 SSE 返回逐文件进度。用户主动重建时，会先清理旧 chunks、文本向量和图片向量，再逐文件重建。

失败策略：

- 单个文件 Embedding 失败不会中断整批重建。
- 失败文件写入 `index_error`，状态保持为未完成。
- 已成功文件继续可用。
- 余额不足或网络异常恢复后，可再次重试失败文件或重新构建索引。
- 检索时向量失败会降级到 FTS5；但语义召回质量会下降。

### 8.4 会话范围与工具边界

会话范围拆为四类状态：

- `read_scope`：允许读取哪些 Markdown 文件。
- `retrieval_scope`：检索召回范围。
- `write_scope`：允许生成修改预览的文件范围。
- `style_scope`：风格参考范围。

模型不负责推断这些范围。旧的 `reference_mode / fact_file_ids / style_mode / style_file_ids` 进入服务端后会转换为会话 scope。

第一阶段工作区工具包括：

- `search_knowledge`
- `read_file`
- `get_style_context`
- `ask_user`
- `preview_edit_article`

其中 `preview_edit_article` 只生成预览，不直接写 Markdown；真正落盘仍由保存接口完成。

## 9. 验收口径

本轮完成后，应满足以下结果：

1. 在任意业务页打开文档，再切到其他业务页时，该文档会自动带入对应页面逻辑。
2. 知识库回答不再只给来源入口，而是结合召回证据做整理总结。
3. 知识库来源点击后留在知识库页，并在左侧编辑区定位原文。
4. 创作页能区分“事实参考”和“风格来源”，且当前文档真实参与 AI 生成链路。
5. 创作块切分优先遵循标题层级和语义结构，而不是简单按字符串拆段。
6. 侧边栏折叠状态、文件树展开状态、文件树 / 大纲 tab 保持持久化；同一文档在文件页、知识库页和创作页之间恢复最近阅读位置。
7. 知识库回答能够展示本次读取了哪些 Markdown 文档，并区分完整正文与节选正文。
8. 文件索引失败时必须留下可见状态，不能把未完成向量化的文件当成已完成。

## 10. 画布规划层 LLM 优先升级（2026-05-24）

### 背景

原规划层用正则打分（`inferIntentCandidates`）决定 `primary_intent`，`topScore=0` 时 `ambiguous=false`，导致 LLM 仲裁永远不触发，"将 Bun 换为 Node.js"这类不含操作动词的替换指令被静默降级为聊天模式。

### 变更内容

1. **删除正则意图层**：移除 `inferIntentCandidates`、`resolvePrimaryIntent`、`inferOperationKind`、`inferOperationCandidates` 四个函数
2. **LLM 成为唯一意图决策者**：`resolveCanvasRequest` 每次请求都调用 `runHelperPlanner(mode='target_resolver')`，由 LLM 判断 `primary_intent / operation_kind / target_refs / scope_mode / clarify_needed`
3. **正则退为词法辅助**：`parseExplicitMentionIds`（@b 引用）、`isGlobalPhrase`（全文/整篇）、`extractDeterministicRewrite`（精准替换句式，补全支持"换为/替换成"）保留，作为候选上下文传入 LLM，不作为决策依据
4. **Prompt 强化**：`buildCanvasQueryPlanPrompt` 的 `target_resolver` 模式加入明确的意图判断规则和示例，确保弱模型（DeepSeek）也能正确识别替换句式；缺少明确修改动词时不再默认偏向编辑，只有显式块引用、上一轮编辑建议承接、写入/替换/应用到正文等表达才进入 `edit`
5. **失败保守处理**：LLM 调用失败时返回 `clarify_needed=true + reason=ai_arbitration_unavailable`，不再静默 fallback 到 text

### 影响范围

- `notus/lib/canvasRequestPlanner.js`：主要重构
- `notus/lib/prompt.js`：`target_resolver` 模式 prompt 更新
- 性能：每次请求多一次 LLM 规划调用，命中 3min 缓存时无额外开销
# 2026-06-19 Agent Workspace 调整

- 知识库页和创作页的前端承载方式统一为 Agent Workspace；底层知识库检索、创作规划、operation set 和文件保存链路继续复用现有实现。
- 工具过程不新增通用 Agent Loop，而是由现有 SSE 事件映射：知识库映射检索和回答，创作映射 thinking、batch 进度和修改预览。
- 搜索服务商进入配置保存阶段，当前请求会携带联网状态和服务商，但不调用真实外部搜索。
