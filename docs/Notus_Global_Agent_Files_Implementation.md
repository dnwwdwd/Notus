# Notus 全局 Agent 文件技术实现文档

## 1. 背景

Notus 需要为内置 Agent 提供一组长期生效、用户可以查看和修改的全局文件，用来描述 Agent 的性格、写作风格和跨会话记忆。

第一阶段只实现以下三个文件：

```text
soul.md
style.md
memory.md
```

本次不增加 `rules.md`、`AGENTS.md`、`USER.md`、`TOOLS.md` 等其他文件。后续是否拆分，根据实际使用中三份文件的长度和维护成本再决定。

这三个文件属于 Notus 的全局 Agent 配置，不跟随单篇笔记或单个项目切换。用户在任何知识库、目录或会话中使用 Notus Agent 时，都可以按对应规则读取这些文件。

---

## 2. 实现目标

完成后，Notus 应具备以下能力：

- 首次启动时自动创建三份默认文件。
- 用户可以在设置页面查看和编辑三份文件。
- Agent 可以读取三份文件，并按不同场景注入上下文。
- `soul.md` 长期影响 Agent 的性格和沟通方式。
- `style.md` 只在写作、改写、润色等任务中生效。
- `memory.md` 保存跨会话有效的用户偏好、项目背景和已确认决策。
- Agent 可以提出或执行记忆更新，但不能随意把临时内容写入长期记忆。
- Electron、普通 Web 部署和懒猫微服使用同一套文件管理逻辑。
- 文件修改后，不需要重启 Notus 即可在后续请求中生效。
- 用户可以恢复默认内容，也可以查看历史版本并回滚。

三份 Markdown 文件用于给模型提供上下文，不承担系统权限控制。文件中的内容不能绕过 Notus 的工具权限、路径授权、危险操作确认和系统安全规则。

---

## 3. 文件职责

### 3.1 soul.md

`soul.md` 描述 Agent 的长期性格和沟通倾向。

适合保存：

- Agent 的角色定位。
- 回答时的语气。
- 面对分歧时的态度。
- 面对不确定信息时如何表达。
- 是否主动指出方案缺陷。
- 如何处理用户情绪。
- 对隐私和外部操作的基本态度。
- 长期稳定的行为风格。

不适合保存：

- 当前项目技术栈。
- 一次性任务要求。
- 具体写作格式。
- 用户的临时偏好。
- API、路径和工具配置。
- 可以由代码强制执行的权限规则。

建议默认内容保持简短。它应描述 Agent 的人格，不要写成完整系统 Prompt。

示例：

```markdown
# Agent 性格

你是 Notus 内置的知识与写作 Agent。

保持直接、冷静和具体。发现方案存在明显问题时直接指出，不为了迎合用户省略风险。

无法确认的信息要明确说明，不根据模糊上下文补造事实。

尊重用户的原始判断和表达习惯。涉及删除、覆盖、发布等高风险操作时，确认用户意图。
```

### 3.2 style.md

`style.md` 描述用户希望 Agent 在写作任务中遵守的表达规则。

适合保存：

- 常用语气。
- 段落长度。
- 标题习惯。
- 是否使用列表。
- 是否保留第一人称。
- 技术术语的处理方式。
- 禁用词和禁用句式。
- 公开文章、技术文档、社交内容的写法。
- 用户对“AI 味”的具体判断标准。

不适合保存：

- Agent 人格。
- 用户项目状态。
- 长期技术决策。
- 工具权限。
- 普通问答必须遵守的流程。
- 与写作无关的运行配置。

`style.md` 不应在所有请求中完整注入。只有任务涉及写作、改写、润色、续写、翻译后的文字调整、文章整理等场景时才加载。

普通技术问答、文件检索、MCP 调用、数据库查询等任务不需要加载完整写作规则，避免增加无效 token，也避免写作要求干扰工具执行。

示例：

```markdown
# 写作风格

保留事实、数字、产品名、模型名、日期和工程细节。

作者亲自做过的事情使用第一人称和完成时，例如“我测了”“我保留了”“我删掉了”。

保留 Agent、LLM、token、API、Claude、Codex 等中文技术圈常用英文术语。

减少讲义式结构、空洞总结和过度完整的段落。优先保留具体测试、成本和工程细节。

不要添加原文没有的例子、数据和个人经历。
```

### 3.3 memory.md

`memory.md` 保存跨会话仍然有价值的信息。

适合保存：

- 用户长期稳定的偏好。
- 用户常用技术栈。
- Notus 等长期项目的背景。
- 已经确认的技术路线。
- 已经做出的产品决策。
- 需要长期避免的历史问题。
- 后续会反复使用的上下文。
- 用户明确要求记住的信息。

不适合保存：

- 原始聊天记录。
- 当天临时任务。
- 已经过期的短期状态。
- 一次性文件路径。
- 可以从当前项目重新读取的普通代码信息。
- 未经确认的推测。
- 大段原文、日志和实现文档。
- 敏感凭据、Token、密码和 API Key。

建议在文件内使用稳定章节，方便 Agent 定位和更新：

```markdown
# 全局记忆

## 用户偏好

## 常用技术栈

## 长期项目

## 已确认决策

## 重要经验
```

第一阶段可以使用单文件。内容增长后，可以再引入分片文件或数据库检索，不需要在本次实现中提前设计复杂的记忆系统。

## 4. 文件存储

三份文件应放在 Notus 的应用数据目录中，不放进程序安装目录，也不跟随软件升级被覆盖。

逻辑结构：

```text
<notus-data>/
└── agent/
    ├── soul.md
    ├── style.md
    ├── memory.md
    └── history/
```

实际根目录通过 Notus 现有的运行环境和数据目录抽象获取，不要求业务代码直接拼接固定绝对路径。

### Electron

使用 Electron 当前用户数据目录下的 Notus 持久化目录。

要求：

- Windows、macOS 和 Linux 路径由 Electron API 统一解析。
- 不依赖当前工作目录。
- 应用升级后继续保留。
- 多窗口共享同一份文件。
- 渲染进程不能直接访问任意系统路径，文件读写通过后端或 Electron Bridge 完成。

### 普通 Web 部署

使用服务端持久化数据目录。

要求：

- 容器部署时挂载持久化卷。
- 服务重启后文件保留。
- 多个请求通过统一服务访问文件。
- 不依赖浏览器本地存储。

### 懒猫微服

使用懒猫允许的应用持久化目录。

要求：

- 三份文件只能写入 Notus 自己的持久化空间。
- 应用更新或容器重启后保留。
- 不扫描或写入其他应用的数据目录。
- 与普通 Web 端复用相同的文件服务接口。

具体路径由现有懒猫部署配置决定，文档不固定某个绝对路径。

---

## 5. 首次初始化

Notus 启动时检查三份文件是否存在。

处理规则：

- 文件不存在时，从内置模板创建。
- 文件已存在时，不覆盖用户内容。
- 某一份文件丢失时，只补建缺失文件。
- 内置模板升级时，不自动覆盖旧文件。
- 模板版本可以记录在配置或数据库中，用于提示用户有新模板可参考。
- 创建失败时记录错误，并在设置页面提示。

默认模板只提供基础结构和少量示例，不预先写入大量规则。

建议把默认模板随应用打包，并通过文件服务完成初始化。不要把默认正文分散硬编码在多个前端组件中。

## 6. 加载策略

### soul.md

每次创建 Agent 请求时加载。

它属于长期人格上下文，但需要控制长度。建议提供：

- 文件内容读取。
- 内容 Hash 缓存。
- 长度限制。
- 超限提示。
- 文件变更后缓存失效。

### style.md

仅在写作类任务中加载。

写作任务至少包括：

- 创作文章。
- 改写。
- 润色。
- 续写。
- 调整语气。
- 生成完整邮件或公开文本。
- 将草稿整理成可发布内容。

是否属于写作任务，可以结合当前 Agent Loop 的意图判断、用户明确指令和所调用的写作 Tool 决定。

意图判断不确定时，可以加载一份压缩后的风格摘要，或者等 Agent 确认需要写作后再读取完整文件。

### memory.md

每次请求都可能需要，但不建议无限制全量注入。

第一阶段可以采用简单策略：

- 文件较短时完整加载。
- 文件超过设定预算时，优先加载稳定摘要。
- 用户问题明确涉及某个长期项目或偏好时，再检索相关章节。
- 记忆更新后使缓存失效。

Notus 已有知识库检索能力时，可以在后续版本将较长的全局记忆分块索引。本阶段不要求为三份文件建立独立向量数据库。

---

## 7. 上下文顺序

建议的上下文组合顺序：

```text
系统安全规则和工具权限
        ↓
Notus 固定系统指令
        ↓
soul.md
        ↓
memory.md 中与本轮有关的内容
        ↓
当前笔记、用户选择的文件、知识库和附件
        ↓
style.md（仅写作任务）
        ↓
本轮匹配的 Skill
        ↓
用户当前请求
```

具体顺序可以结合当前 Agent Loop 调整，但必须满足：

- 系统安全规则高于三份用户文件。
- `style.md` 不能覆盖事实和项目上下文。
- `memory.md` 不能覆盖用户当前消息中的新要求。
- Skill 的具体流程不能修改 Agent 的全局人格文件。
- 三份文件中出现冲突时，以用户当前明确要求和更高层规则为准。

## 8. 设置页面

在 Notus 设置页面增加“全局 Agent”或“Agent 个性化”入口。

页面包含三个编辑项：

- Agent 性格。
- 写作风格。
- 全局记忆。

每个编辑项至少支持：

- 查看当前内容。
- Markdown 编辑。
- 保存。
- 取消修改。
- 恢复默认模板。
- 查看最后更新时间。
- 查看当前字数或字符数。
- 超过推荐长度时提示。
- 打开历史版本。
- 回滚到某个历史版本。

编辑器可以复用 Notus 当前 Markdown 编辑能力，不需要重新开发完整编辑器。

页面应明确说明：

- `soul.md` 影响 Agent 的性格和沟通方式。
- `style.md` 只在写作任务中使用。
- `memory.md` 保存长期有效的信息。
- 文件内容不能修改系统权限和安全限制。

用户不需要看到真实系统绝对路径。可以提供“打开文件所在位置”作为 Electron 环境下的附加功能。

---

## 9. 文件读写服务

三份文件通过统一服务访问。

该服务负责：

- 初始化。
- 读取。
- 保存。
- 校验。
- 历史版本。
- 恢复默认。
- 缓存失效。
- 文件变更通知。
- 错误处理。
- 运行环境路径解析。

模块如何命名、放在哪一层，由执行模型结合 Notus 当前架构决定。

前端页面、Agent Loop 和 Agent Tool 不应分别直接读写文件。

统一调用关系：

```text
设置页面 ─────┐
              │
Agent Loop ───┼── 全局 Agent 文件服务
              │
Agent Tool ───┘
```

## 10. Agent 修改文件

用户可以手动编辑三份文件，也可以允许 Agent 帮助维护。

建议提供受控 Tool，例如：

- 读取全局 Agent 文件。
- 更新 `memory.md`。
- 更新 `style.md`。
- 更新 `soul.md`。

具体 Tool 名称结合现有 Notus Tool 命名方式确定。

### memory.md

Agent 可以在以下情况下提出写入：

- 用户明确要求记住某项信息。
- 用户确认了长期技术决策。
- 某项偏好在后续会话中仍然有价值。
- 某个问题重复出现，已有稳定解决方法。
- 长期项目状态发生重要变化。

Agent 不应因为普通对话自动保存全部信息。

推荐流程：

```text
发现候选记忆
    ↓
整理成简短条目
    ↓
检查是否重复或冲突
    ↓
更新对应章节
    ↓
保存历史版本
    ↓
后续请求生效
```

是否每次都需要用户确认，可以由产品策略决定：

- 用户明确说“记住”时直接更新。
- Agent 主动识别的候选记忆默认询问。
- 项目自动状态不写入全局记忆，除非它具有长期价值。

### style.md

Agent 修改 `style.md` 时应更加谨慎。

适合修改的场景：

- 用户明确要求以后都采用某种写法。
- 用户明确增加禁用句式。
- 用户确认某种输出格式作为长期偏好。

一次性文章要求不写入 `style.md`。

### soul.md

`soul.md` 属于 Agent 人格。默认只有用户明确要求时才修改。

Agent 不应根据单次对话自行改变人格。

修改后建议在界面中明确提示，并保留可回滚版本。

## 11. 内容校验

保存时至少执行以下校验：

- 文件编码为 UTF-8。
- 文件名固定，不能由输入参数指定任意路径。
- 单文件大小不超过配置上限。
- 内容不是二进制。
- 保存采用临时文件和原子替换，避免中途失败产生空文件。
- 写入前保留历史版本。
- 防止路径穿越。
- 不允许符号链接把文件指向 Notus 数据目录之外。
- 内容为空时给出确认或保留基础标题。

Markdown 内容不需要严格 Schema。用户应保留自由书写空间。

---

## 12. 长度和 token 控制

三份文件不能无限增长并每轮完整注入。

建议设置推荐长度和硬上限，具体数值结合当前模型上下文和 Notus Prompt 预算确定。

处理原则：

- 接近推荐长度时在设置页面提示。
- 超过注入预算时不截断原文件，只在模型上下文中压缩或选择相关内容。
- 超过硬上限时拒绝继续自动追加，并提示用户整理。
- `soul.md` 和 `style.md` 应尽量短。
- `memory.md` 可以较长，但需要章节化和去重。
- 不要让 Agent 每次更新时只在文件末尾追加。

记忆整理应优先：

- 合并重复条目。
- 删除已经失效的状态。
- 把长描述压缩为结论。
- 保留日期，只在日期会影响判断时使用。
- 保留用户明确要求的原始措辞。

---

## 13. 缓存和文件监测

为避免每次请求重复读取磁盘，可以使用内存缓存。

缓存至少包含：

- 文件内容。
- 内容 Hash。
- 最后修改时间。
- 解析后的章节信息。

缓存失效场景：

- 设置页面保存。
- Agent Tool 更新。
- 恢复默认。
- 历史版本回滚。
- Electron 环境下检测到外部编辑。
- Web 或懒猫环境下文件修改时间变化。

Electron 可以使用文件监听器监测用户在外部编辑器中的修改。

Web 和懒猫环境可以优先依赖应用内保存操作，并在读取时通过修改时间或 Hash 做低成本检查，不要求为网络文件系统引入复杂监听机制。

---

## 14. 历史版本与回滚

每次保存前创建历史版本。

历史记录至少保存：

- 文件类型。
- 修改时间。
- 修改来源。
- 内容 Hash。
- 完整内容或可恢复快照。

修改来源可以区分：

- 用户在设置页面修改。
- Notus Agent 修改。
- 系统首次初始化。
- 恢复默认。
- 历史回滚。
- Electron 外部文件修改。

历史保留数量或时间由配置决定。第一阶段使用有限数量的完整快照即可，不需要设计复杂 Diff 存储。

回滚本身也生成新的历史记录，避免覆盖历史链路。

---

## 15. 数据库与文件的关系

Markdown 文件是三份配置的内容来源。

数据库或现有配置系统可以保存：

- 是否启用某份文件。
- 模板版本。
- 最后成功加载时间。
- 内容 Hash。
- 历史记录索引。
- 推荐长度和上限。
- 写入策略。
- Agent 是否允许主动提出记忆更新。

不要同时在数据库和 Markdown 文件中保存两份独立正文，避免内容不一致。

正文以文件为准，数据库只保存元数据和索引。

---

## 16. API 或 IPC

设置页面和 Agent Loop 通过现有后端能力访问三份文件。

需要覆盖以下操作：

- 获取文件列表及状态。
- 读取指定文件。
- 保存指定文件。
- 恢复默认。
- 获取历史版本。
- 回滚历史版本。
- 获取当前生效摘要。
- 触发缓存刷新。

实际使用 HTTP API、Server Action、Electron IPC 或内部 Service，由现有架构决定。

所有入口最终调用同一文件服务，不在多个入口重复实现权限和保存逻辑。

---

## 17. 错误处理

至少处理以下错误：

- 应用数据目录不可写。
- 文件初始化失败。
- 文件读取失败。
- 文件编码异常。
- 文件超出大小限制。
- 保存时内容已被其他进程修改。
- 历史版本创建失败。
- 回滚目标不存在。
- Markdown 内容为空。
- 文件监测失效。
- 缓存与磁盘内容不一致。

错误处理要求：

- 不把系统绝对路径和堆栈直接展示给普通用户。
- 设置页面提供可理解的错误说明。
- 保存失败时保留用户编辑内容。
- Agent 加载失败时继续处理当前请求，但明确记录哪份上下文没有加载。
- `memory.md` 加载失败不能导致所有聊天不可用。
- 多进程或多实例写入冲突时，避免静默覆盖。

---

## 18. 安全边界

三份文件属于用户可控 Prompt，上下文中可能出现错误规则或 Prompt Injection。

实现时需要满足：

- 三份文件的优先级低于系统安全规则。
- 文件内容不能直接开启未授权 Tool。
- 文件内容不能修改 MCP、文件系统和网络权限。
- 文件中写了“自动删除”也不能绕过危险操作确认。
- 不执行 Markdown 中的 Shell 命令。
- 不解析并自动加载文件里引用的任意本地路径。
- 不在 `memory.md` 中保存密钥和认证信息。
- Agent 更新时只允许操作三份固定文件。
- Agent Tool 不接受任意绝对路径参数。

## 19. 测试要求

### 初始化

- 三份文件都不存在时能自动创建。
- 只缺一份时只补建缺失文件。
- 应用升级不会覆盖用户内容。
- Electron、Web 和懒猫环境都能正确获取数据目录。

### 加载

- 普通问答加载 `soul.md` 和相关记忆。
- 写作任务额外加载 `style.md`。
- 非写作任务不注入完整 `style.md`。
- 文件更新后下一轮请求使用新内容。
- 文件过长时上下文控制有效。

### 编辑

- 用户可以保存三份文件。
- 保存前生成历史版本。
- 恢复默认后可以回滚。
- 保存失败不会丢失编辑内容。
- 并发修改能发现冲突。

### Agent 更新

- 用户明确要求记忆时能更新 `memory.md`。
- 一次性要求不会自动写入长期记忆。
- Agent 不会自行修改 `soul.md`。
- 重复记忆不会反复追加。
- 更新后能追踪修改来源。

### 运行环境

Electron：

- 外部编辑器修改文件后能检测变化。
- 多窗口看到一致内容。
- 应用升级后文件保留。

普通 Web：

- 服务重启后文件保留。
- 多请求读写一致。
- 容器部署挂载持久化目录后正常工作。

懒猫微服：

- 应用重启和升级后文件保留。
- 文件只位于 Notus 应用持久化空间。
- 不依赖 Electron API。

## 20. 验收标准

实现完成后应满足：

1. Notus 自动创建 `soul.md`、`style.md` 和 `memory.md`。
2. 三份文件保存在应用持久化数据目录。
3. 用户可以在设置页面查看、编辑和恢复三份文件。
4. `soul.md` 在 Agent 请求中长期生效。
5. `style.md` 只在写作类任务中生效。
6. `memory.md` 可以保存跨会话长期信息。
7. Agent 可以受控地更新 `memory.md`。
8. Agent 不能自行改变 `soul.md`。
9. 每次修改都有历史版本和修改来源。
10. 文件修改后不需要重启应用。
11. Electron、普通 Web 和懒猫微服共用一套业务实现。
12. 文件内容不能绕过系统权限和危险操作确认。
13. 文件过长时不会无条件全部塞入模型上下文。
14. 原有 Agent Loop、知识库、文件编辑和 MCP 功能不受影响。
15. 第一阶段不引入其他全局 Agent 文件。
